# ClipBridge wire protocol, v1

Normative spec. The Python (`windows/`) and Kotlin (`android/`) implementations must
follow it exactly and must pass `protocol/test_vectors.json` (generated by
`protocol/gen_vectors.py`). If this file and an implementation disagree, this file wins.

Notation: `‖` is byte concatenation. `"x"` in a byte context is the ASCII bytes of x.
"b64" is standard base64 (RFC 4648 section 4, alphabet `A-Z a-z 0-9 + /`) **with `=` padding**,
no line breaks. Decoders reject any other alphabet, missing padding, or wrong decoded length.

## 1. Roles and transport

- **Server** = Windows laptop. WebSocket server on `0.0.0.0:8765`, advertised over mDNS as
  `_clipbridge._tcp.local.` (port in the SRV record). Accepts any number of clients.
- **Client** = Android device. Connects to `ws://<host>:8765/`.
- Two connection kinds share the port, told apart by the WebSocket subprotocol:
  - `clipbridge.v1`: the **control connection**. One per client; carries every feature message.
  - `clipbridge.data.v1`: a **data connection**. Carries only file-transfer bytes (section 6.3),
    so a large file never delays control messages. A client opens zero or more of them.
  The client must offer exactly one of the two; the server must reject the HTTP upgrade (HTTP 400)
  if neither is offered; the client must abort if the server did not select the one it offered.
- Both kinds use the same handshake (section 3), keys (section 4) and frames (section 5).
- After the handshake the link is symmetric: both sides send and receive the same frame format
  and features do not know which side is the server.

## 2. Device keys and identities

- **device**: client identifier, 1 to 64 characters from `[A-Za-z0-9._-]` (so its UTF-8 bytes are
  its ASCII bytes). Stable per install. The server has no identifier. Device ids are not secret.
- **PSK**: each paired device has its **own** 32-byte key from a CSPRNG, generated by the server
  when that device is paired and given to it during pairing (as b64). Never sent over the network.
  Wherever this spec says PSK it means the PSK of the device named in `auth`.
- **Device registry** (server): `{device: {psk, name}}`, one entry per paired device. `name` is a
  human-readable label for the UI (the device's latest `hello` name, section 6.1). How the registry
  is stored is an implementation detail (informative: Windows keeps it DPAPI-protected for the
  current user).
- **Pairing** a device creates its entry; pairing the same device id again replaces its key (the
  old key stops working at once). **Unpairing** (revocation) deletes the entry and closes every
  live connection of that device, control and data, with **4401**.
- Because each device holds only its own key, a device cannot authenticate as another device and
  cannot impersonate the server to other devices (a server MAC it can compute is valid only under
  its own key). A lost phone is revoked by unpairing that one device.

## 3. Handshake (plaintext, WebSocket **text** messages, JSON UTF-8)

| # | Direction | Message |
|---|---|---|
| 1 | S → C | `{"type":"challenge","v":1,"sn":"<b64 16 bytes>"}` |
| 2 | C → S | `{"type":"auth","v":1,"cn":"<b64 16 bytes>","device":"<device>","mac":"<b64 32 bytes>"}` |
| 3 | S → C | `{"type":"auth_ok","mac":"<b64 32 bytes>"}` |

- `sn` (server nonce) and `cn` (client nonce): 16 bytes each from a CSPRNG, fresh per connection.
- Client MAC: `HMAC-SHA256(key=PSK of device, msg="c" ‖ sn ‖ cn ‖ device_utf8)`. The literal `"c"` is the
  single byte `0x63`; `sn` and `cn` are the raw 16-byte values (not b64); total input length is
  `33 + len(device)`.
- Server MAC: `HMAC-SHA256(key=PSK of device, msg="s" ‖ sn ‖ cn)`. `"s"` is the byte `0x73`; input is 33 bytes.
- JSON key order and whitespace are free. Unknown keys are ignored. Missing/ill-typed keys,
  wrong b64, wrong decoded lengths, or an unexpected `type` → close **4400**.
- `v` ≠ 1 → close **4426**.
- The server looks up `device` in its registry and checks the client MAC with that device's PSK,
  in constant time (`hmac.compare_digest` / `MessageDigest.isEqual`). Unknown `device` or MAC
  mismatch → close **4401** with an empty reason. No `auth_ok` is sent. The two cases need not take
  the same time (device ids are not secret); computing a MAC with a dummy key for an unknown device
  is allowed, not required.
- Client checks the server MAC in constant time. Mismatch → client closes **4401**. The client
  must not send any encrypted frame before this check passes (a rogue server learns nothing).
- The server may send encrypted frames immediately after `auth_ok`. On a control connection the
  first frame each side sends is `hello` (section 6.1).
- Timeout: the server closes **4408** if a valid `auth` has not arrived within 10 s of the
  WebSocket opening. The client closes **4408** if the handshake has not finished within 10 s of the
  WebSocket opening (a server that never sends `challenge` cannot hold it).
- The server handles at most **16** unauthenticated connections at once; more are closed **1013**
  (try again later).
- If a client authenticates a **control** connection with a `device` that already has a live
  control connection, the server closes the **older** one with **4409** (stale socket after a
  network change). Data connections never replace anything and are never replaced.

## 4. Session keys

`HKDF-SHA256` (RFC 5869):

| Parameter | Value |
|---|---|
| IKM | PSK of the authenticated device (32 bytes) |
| salt | `sn ‖ cn` (32 bytes) |
| info | `"c2s"` (3 bytes) for client→server; `"s2c"` (3 bytes) for server→client |
| L | 32 bytes |

Equivalently: `PRK = HMAC-SHA256(key=sn‖cn, msg=PSK)`; `key = HMAC-SHA256(key=PRK, msg=info ‖ 0x01)`.
Each side encrypts with its sending key and decrypts with its receiving key. Control and data
connections derive their keys the same way, from the device's PSK and their own fresh nonces.

## 5. Encrypted frames (WebSocket **binary** messages)

After the handshake every message in both directions is one binary WebSocket message:

```
frame = nonce (12 bytes) ‖ AES-256-GCM ciphertext (len(plaintext) bytes) ‖ GCM tag (16 bytes)
nonce = u64 counter, little-endian (8 bytes) ‖ 00 00 00 00
```

- Cipher: AES-256-GCM, 96-bit nonce, 128-bit tag, **empty AAD**. (The nonce is already bound
  by GCM, and the direction is bound by the per-direction key, so no AAD is needed.)
- Counters: each direction has its own counter, starting at **0** on every new connection.
  The sender uses the current value, then increments by 1. The receiver accepts a frame only if
  its counter equals the **next expected value** (0, then 1, 2, ...); WebSocket over TCP is
  ordered, so any gap, repeat, or reorder is an attack or a bug. A sender must close the
  connection (1000) rather than reuse a counter after `2^64 - 1`.
- Receiver order of checks: length ≥ 28, nonce bytes 8..11 all zero, counter == expected,
  GCM decrypt. Any failure → close **4402** (empty reason). Never process a frame that failed.
- After the handshake, a text WebSocket message → close **4400**.

## 6. Envelope (the decrypted plaintext)

```
plaintext = header_len (u32, big-endian) ‖ header (header_len bytes, JSON, UTF-8) ‖ body (rest)
```

- `header` is a JSON object. `body` is raw bytes and may be empty (length 0).
- JSON may use raw UTF-8 or `\uXXXX` escapes (non-BMP characters as escaped surrogate pairs,
  e.g. `😀`); receivers must accept both. Key order and whitespace are free. Senders
  must not emit lone surrogates.
- Malformed envelope (header_len > plaintext length − 4, invalid UTF-8/JSON, header not an
  object, `ch` missing or not a string): drop the message and log a warning. The frame was
  authenticated, so the connection stays open.

### Routing

- **Feature names** are 1 to 64 characters from `[A-Za-z0-9._-]`. Names starting with `link` are
  reserved for the link.
- Every header has `"ch": "<feature name>"`. The link layer delivers `(peer, header, body)` to
  the feature registered under that name. Unknown `ch` → ignore and log at debug level.
- Within a feature, unknown `type` or `kind` values → ignore. Unknown header keys → ignore.
- `ch` values starting with `link` are link-layer messages (sections 6.1 to 6.3). They are
  handled by the link and never delivered to a feature.
- The header key `mid` is reserved for the link (section 6.2); features must not use it.

### 6.1 Hello (`ch = "link"`)

Tells the peer who it is talking to and which features, at which versions, it handles.

```json
{"ch":"link","type":"hello","name":"<device name>","features":{"clipboard":1,"files":1}}
```

- Empty body. Each side sends exactly one `hello`, as its **first** encrypted frame on a
  **control** connection: the server right after `auth_ok`, the client right after the server MAC
  checked out. A first frame that is not a valid `hello`, or a second `hello` → close **4400**.
  Data connections carry no `hello`.
- `name`: human-readable device name for the UI (for example "Pixel 8"), 1 to 64 Unicode code
  points, no control characters (U+0000 to U+001F, U+007F). The server stores the client's `name`
  in its device registry.
- `features`: JSON object of at most 64 entries `"<feature name>": <version>`. Keys are feature
  names (section 6, not starting with `link`); versions are integers from 1 to 2 147 483 647. A
  side lists every feature it has registered, with the highest version it handles. Any violation →
  close **4400**.
- `peer.supports(name, version)` is true when the peer's `hello` lists `name` with a version
  ≥ `version`. The link reports a peer to features (`on_peer_connected`) only once its `hello` has
  arrived, so every peer a feature sees has known capabilities.
- The server relays a feature message only to clients whose `hello` lists that feature. A side
  should not send a feature message whose `ch` the peer's `hello` does not list; a receiver still
  ignores an unknown `ch` (above).

### 6.2 Requests and replies (`ch = "link"`)

Any feature message may be sent as a **request**, so the sender learns that the peer actually
processed it (not only that the bytes left the socket, which says nothing on a half-dead
connection) and, if the feature wants, gets an answer back. A delivery receipt is the empty reply.

- To make a request, the sender's link adds `"mid": "<id>"` to the header: 1 to 64 characters from
  `[A-Za-z0-9._-]`, unique among this sender's unanswered requests on the connection.
- The receiver's link hands the message to the addressed feature, then sends back exactly one
  reply:

  ```json
  {"ch":"link","type":"reply","mid":"<id>","ok":true,"data":{}}
  ```

  - `ok: true`: the feature handled the message without error. The feature may return reply
    content: `data` (a JSON object; absent when the feature returns none) and a body (empty when it
    returns none). With neither, the reply is a plain delivery receipt. A message the feature
    ignores on purpose (for example a duplicate clip) still counts as handled.
  - `ok: false`: the request reached the peer but was not handled: no feature is registered under
    its `ch`, or the feature failed. `data` is absent and the body is empty. The peer answers
    instead of staying silent so that the sender can tell a live peer that failed from a dead
    connection without waiting out the timeout.
  - Reply content counts against the size limit (section 8); a feature whose reply would exceed it
    has failed (`ok: false`).
- A request that never reaches the routing step (malformed envelope, invalid `mid`) gets no reply.
- `ch = "link"` messages never carry `mid` and are never answered. Unknown link `type` → ignore.
- A reply for an unknown `mid` → ignore.
- Sender (informative): a request counts as **not delivered** if no reply arrives within 10 s or
  the connection closes first. Retrying is the feature's (or user's) choice.
- A reply covers only the direct peer. When the server relays a message to other clients, the
  reply does not mean they received it.

### 6.3 File transfer (link service)

Moves one file of any size from the side that has it (**sender**) to the other side
(**receiver**), on behalf of a feature. Control messages travel on the control connection with
`ch = "link"`; file bytes travel on data connections, which authenticate with the same device key as the
control connection. Files are never relayed to other clients.

**Control messages** (control connection, empty body):

| Type | Direction | Header fields |
|---|---|---|
| `xfer_offer` | sender → receiver | `id`, `feature`, `name`, `size`, `meta` |
| `xfer_accept` | receiver → sender | `id`, `ranges` |
| `xfer_reject` | receiver → sender | `id` |
| `xfer_done` | receiver → sender | `id`, `ok` (also the answer to a re-offer of a completed `id`) |
| `xfer_cancel` | either | `id` |

- `id`: 32 lowercase hex characters (16 random bytes), chosen by the sender. A re-offer of the
  same file after a reconnect reuses the same `id`.
- `feature`: name of the feature that handles the file on the receiver (as in `ch`). Unknown
  feature, or the feature declines → `xfer_reject`.
- `name`: file base name, 1 to 255 characters. The receiver strips any path and replaces
  characters its file system forbids; it never writes outside the destination the feature chose.
- `size`: file length in bytes (integer ≥ 0). `meta`: JSON object for the feature (may be `{}`).
- `ranges`: list of `[start, end, have]` integers: the receiver stores bytes `[start, end)` as one
  range, of which the first `have` bytes are already on disk. For a new file `have` is 0. Ranges
  are sorted, do not overlap, and together cover `[0, size)`. The receiver chooses the split (one
  range, or up to one per data connection it wants); on a re-offer it repeats the same split with
  updated `have`. `have` equals the range length only in the answer to a completed `id` (below):
  for an unfinished file a range already fully on disk is reported one byte short, so it still
  ends with `xfer_end` and its hash is checked. A file of size 0 has `ranges = []`.
- `ok`: `true` once every range has arrived and matched its hash and the file is in its final
  place; `false` on a hash mismatch (the receiver discards the partial file and all its state for
  that `id`). After `ok:false` the sender may offer the file once more with a new `id`.
- `xfer_cancel`: both sides drop the transfer; the receiver deletes the partial file. The sender
  stops streaming; open data connections for that `id` are closed (1000). Either side sends it
  when it cannot go on (the receiver cannot write to its storage, the sender cannot read the
  file), on the control connection **before** it closes that transfer's data connection, so the
  peer sees a cancelled transfer rather than a broken link. The sender gives up on a transfer,
  with `xfer_cancel`, when nothing has moved on it for 60 s: no reply to its offer, no hashing of
  a resume prefix, no range bytes accepted by the socket, and no `xfer_done`.
- Messages with an unknown `id` → ignore.
- A sender should have up to **3** files per peer in flight at once (offered, not yet ended by
  `xfer_done`, `xfer_reject` or `xfer_cancel`), so a small file never waits for a large one to
  finish; further files wait in order. A receiver handles any number.

**Data connections** (subprotocol `clipbridge.data.v1`):

- Always opened by the **client**, whichever side is the sender (the client does not accept
  inbound connections). The client opens them after `xfer_accept` is sent or received, one per
  range it streams at a time.
- The client's first frame on it is `{"ch":"link","type":"xfer_attach","id":"<id>","start":<start>}`,
  naming one accepted range whose `have` is less than its length (a range the receiver already
  has in full gets no data connection). The server replies nothing; unknown `id` or `start` →
  close **4404**.
- Then the **sender** of the file (client or server) sends, in order:
  - `{"ch":"link","type":"xfer_data"}` frames whose bodies are consecutive file bytes from
    `start + have` up to `end` (body 1 byte to 4 MiB each);
  - then `{"ch":"link","type":"xfer_end","sha256":"<64 hex>"}`: SHA-256 of the whole range
    `[start, end)`, including the `have` bytes already on disk (both sides hash that prefix from
    local storage).
- Bytes past `end`, an `xfer_end` before `end`, or any other message type → close **4400**.
- After `xfer_end` the client may send another `xfer_attach` on the same connection (one
  connection carries many ranges and files back to back), or close it (1000).
- The receiver sends `xfer_done` on the control connection once every range of the file has ended.
- If the control connection closes, both sides close that client's data connections. The sender
  re-offers every file it has not seen `xfer_done` for after reconnecting; the receiver answers
  with its current `have` values. How long a receiver keeps partial files of an unfinished `id` is
  its choice.
- The receiver remembers the `id`s it completed with `ok:true` in the last 24 h (with the
  sender's device and `size`; a bounded number, kept in storage so a restart keeps them), because
  that `xfer_done` may have been lost with the connection. A re-offer of a remembered `id` from the
  same device with the same `size` is answered with
  `xfer_accept` whose ranges all have `have` equal to their length, then at once `xfer_done`
  `ok:true`; the file is not received or handed to the feature again.

## 7. Clipboard feature (`ch = "clipboard"`)

Text clip (v1):

```json
{"ch":"clipboard","type":"clip","kind":"text","data":"<clipboard text>","ts":1700000000000}
```

- `data`: full clipboard text as a JSON string (Unicode preserved end to end). `body` is empty.
- `ts`: sender wall clock, milliseconds since Unix epoch (integer). Informational only.
- The server relays every accepted clip to all other clients whose `hello` lists `clipboard`.
- Echo/loop suppression is local state (SHA-256 of the text's UTF-8 bytes); see `SyncEngine` in
  `docs/PLAN.md`. Nothing about it is on the wire.
- Delivery (informative): clips are sent as requests (section 6.2). A clip that is not delivered
  (no reply, or the connection closed first) stays that peer's pending clip, the latest one only,
  and is sent again when the peer reconnects.

Image clip:

```json
{"ch":"clipboard","type":"clip","kind":"image","mime":"image/png","ts":1700000000000}
```

- `body`: the image as PNG bytes. `data` is absent. `mime` is always `"image/png"`; senders convert
  any other source format (JPEG, DIB, WebP, ...) to PNG before sending. Receivers ignore an image
  clip whose `mime` is not `"image/png"` or whose `body` is empty.
- If the envelope would exceed the size limit (section 8), the sender skips it and logs.
- Echo/loop suppression uses SHA-256 of the PNG bytes in the **same** single `last_hash` slot as
  text (text and images share it; last writer wins).
- The server relays image clips like text clips.
- Receiver behaviour (informative): Windows puts the image on the clipboard (`PNG` + `CF_DIB`) and
  saves it to `%USERPROFILE%\Pictures\ClipBridge\`; Android puts a FileProvider `content://` URI on
  the clipboard.

## 8. Size limits

- Maximum plaintext (envelope) size: **16 MiB = 16 777 216 bytes**. Maximum WebSocket message:
  16 777 216 + 28 bytes. Handshake messages: 4 KiB max, enforced per frame by both sides before
  authentication (the 16 MiB limit applies only after `auth_ok`).
- A sender must not send an envelope above the limit: skip it and log.
- A receiver must reject larger messages; the WebSocket library closes with **1009**.

## 9. Liveness and reconnect

- WebSocket ping/pong (control frames, not encrypted).
- Server: ping every **10 s**; close if no pong within **10 s**.
- Server: a connection that accepts no outgoing bytes for **20 s** while a send is pending is
  dropped (a ping cannot detect this: it waits behind the same full write buffer).
- Server (informative): relays and replies are queued, never delaying reading from the sending client, so a
  slow or vanished client cannot hold back another client's replies.
- Client (OkHttp `pingInterval`): ping every **15 s**; connection fails if a pong is missing by the next ping.
- Client reconnect backoff (informative): 1 s doubling, capped at **10 s**, ±20 % jitter, reset
  after a successful handshake; retry immediately on a new network.

## 10. Close codes

| Code | Meaning | Sent by |
|---|---|---|
| 1000 | Normal close | either |
| 1001 | Going away (shutdown) | either |
| 1009 | Message too big | either (library) |
| 1013 | Try again later (too many connections still in the handshake) | server |
| 4400 | Protocol violation (malformed/unexpected handshake message, missing or invalid `hello`, text frame after handshake) | either |
| 4401 | Authentication failed (unknown device or bad MAC), or device unpaired. Reason always empty | either |
| 4402 | Frame integrity failure (bad length, nonce padding, counter, or GCM tag) | either |
| 4404 | Data connection attached to an unknown transfer `id` or range | server |
| 4408 | Handshake timeout | either |
| 4409 | Replaced by a newer connection with the same `device` | server |
| 4426 | Unsupported protocol version | server |

## 11. Test vectors (`test_vectors.json`)

All byte strings are lowercase hex; `*_b64` fields give the same bytes in the wire encoding.
Fields: `psk` (the test device's PSK), `sn`, `cn`, `device`, `client_mac_input`, `client_mac`, `server_mac_input`,
`server_mac`, `key_c2s`, `key_s2c`, and `frames[]`. Each frame has `direction` (selects the key),
`counter`, `nonce`, `header` (parsed), `header_utf8`, `body`, `plaintext` (the full envelope) and
`frame` (the full binary WebSocket message). The frames include a `hello` in each direction, a
request, an empty reply (delivery receipt) and a reply with `data` and a body.

Implementations must test: both MACs, both keys, `encrypt(key, counter, plaintext) == frame`,
`decrypt(frame) == plaintext`, and envelope parsing of `plaintext` into `header` and `body`.
Use the given `plaintext` bytes for the encrypt test: JSON serializers differ in byte output,
which this protocol allows, so do not compare re-serialized headers byte for byte.
